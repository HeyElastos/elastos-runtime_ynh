Elastos Runtime
+ Hey

A sovereign-by-default browser runtime. Signed capsules, explicit capabilities, post-quantum E2E, peer-to-peer transport. Your data lives on your box. Your identity is a passkey.

Rust + axum iroh + iroh-blobs ML-KEM-768 hybrid WebAuthn PRF AES-256-GCM at rest

01The runtime

One Rust binary, sovereign and local, brokers every sensitive operation. Capsules can't open sockets, can't read disk directly, can't reach the network. They ask the runtime; the runtime checks capabilities; the runtime acts.

02The provider zoo

Each provider owns a slice of capability — storage, identity, networking — and exposes operations the runtime brokers to capsules. Some are in-process Rust modules; the rest run as separate native binaries supervised by systemd.

03Namespaces — the URI dialect

Two schemes, both first-class. Every capability is scoped by a URI pattern; every resource the runtime knows about has a canonical URI name.

localhost://

Storage paths

localhost://Users/self/.AppData/Identity/profile.json
localhost://Users/self/.AppData/LocalHost/Hey/posts/<id>.json
localhost://Users/self/.AppData/SystemServices/Shell/active.json
localhost://Users/self/MyWebSite/index.html
localhost://Users/self/Public/*

Identity is shared across capsules. LocalHost is per-capsule private. MyWebSite + Public are plaintext on purpose (public web hosting). Everything else is encrypted at rest.

elastos://

Provider operations

elastos://peer/*              // Carrier gossip + DHT
elastos://peer/hey-v0/*       // app-scoped topics
elastos://blobs/*             // iroh-blobs transfer
elastos://ipfs/*              // Kubo bridge
elastos://did/*               // resolve/sign/verify
elastos://hey-transcoder/*    // avif/h264 worker

Token may cover a whole scheme or narrow to a specific topic. The validator does bidirectional pattern matching — a manifest declaring the broad pattern auto-grants the narrow request.

How a capsule gets access

  • Manifest declaration at install time — capsule.json lists every localhost:// and elastos:// pattern the capsule needs.
  • Capability request at runtime — capsule POSTs { resource, action }; runtime checks against manifest; auto-mints a token bound to (session.id, resource, action).
  • No chmod 777 shortcut. A capsule cannot reach storage or messaging it didn't declare at install. Tokens are bearer-style with exact-action matching (read ≠ write ≠ execute).

04Four security perimeters

Defense in depth. Each layer holds independently — break one and the next still protects the user's data.

1 · transport

nginx terminates TLS in front of the runtime · the daemon binds 127.0.0.1:3000 so no LAN request reaches it without going through the proxy.

2 · auth gate

Every session starts in PreAuth · storage/provider calls 401 · graduates only via passkey signature or PBKDF2 PIN · HMAC-signed cookie carries the proof across capsules.

3 · capabilities

Per-(session, resource, action) tokens · bounded by the capsule's declared manifest · exact-action match means a read token can't write.

4 · at rest

AES-256-GCM envelope under Users/* · key generated once, never overwritten · backup tarball alone gives an attacker ciphertext only.

05Carrier — how messages move

iroh under the hood. Holepunched QUIC, mDNS for LAN, Kademlia DHT for global, iroh-gossip (HyParView + Plumtree) for epidemic broadcast. No central server. Direct peer paths whenever possible; relay only as fallback.

Topics

32-byte ids, usually BLAKE3("<app>/<purpose>/<scope>"). No central registry. DMs use a deterministic topic id from the sorted DID pair.

Discovery

mDNS on LAN (instant), Kademlia DHT globally, address-lookup-mdns to bypass the DHT when you're on the same network.

Connectivity

Direct UDP → STUN holepunching → iroh-relay fallback only when symmetric / CGNAT blocks holepunching.

06Hybrid post-quantum E2E

DMs in Hey Chat are encrypted with X25519 and ML-KEM-768 (NIST FIPS 203, formerly Kyber-768). Breaking the message requires breaking both primitives. Forward-secret per message. Same hybrid pattern as Signal's PQXDH and the NIST transition guidance.

Why hybrid, not pure PQ?

ML-KEM-768 in @noble/post-quantum is self-audited only. Pure PQ would put us at the mercy of any flaw in the implementation or in ML-KEM itself. Hybrid means a bug in either primitive still leaves the message protected by the other.

What's NOT PQ yet

Identity signatures (Ed25519 — for post authorship + DM auth) are still classical. Future: layer ML-DSA-65 alongside. Carrier transport TLS uses classical ECDH — but the PQ layer sits above it, so a transport break just exposes ciphertext.

Resolve recipient's keys

Look up Bob's x25519_pk + kem_pk from his published identity record · cached locally, refreshed via Carrier on miss.

Encrypt the text (hybrid PQ)

X25519 ephemeral + ML-KEM-768 encapsulation → HKDF → ChaCha20-Poly1305 over the plaintext. Wire: { eph_pk, kem_ct, nonce, ct }.

Optional: stage an attachment

If the message carries a file: POST /api/provider/blobs/add_bytes · provider stores under $DATA_DIR/blobs/ and returns an iroh-blobs ticket. Ticket goes into the encrypted payload.

Sign + send over Carrier

Sign the ciphertext payload with Alice's Ed25519 seed · gossip_send on the deterministic DM topic BLAKE3("hey-v0/dm/<sortedDidPair>").

Bob receives + decrypts

gossip_recv · verify signature · decrypt (hybrid PQ reverse) · render. The ciphertext on the wire is PQ-secure: a "harvest now, decrypt later" attacker gets nothing in 2040.

Fetch attachment (if present)

UI shows "📎 photo.jpg · Tap to download". Tap → POST /api/provider/blobs/fetch with the ticket · bytes flow directly Alice→Bob over holepunched QUIC. No third-party storage, no upload step.

09What survives an upgrade

The runtime separates code from state. The $DATA_DIR tree (default ~/.local/share/elastos) holds everything the user owns; replacing the elastos binary leaves it untouched. Capsule bundles refresh, identity and history do not.

StateSurvives?Why
Encryption key .localhost-key yes Generated once at install · install/upgrade scripts only create when missing, never overwrite
Identity profile.json, passkey creds yes Lives in $DATA_DIR under encrypted envelope · same key decrypts after upgrade
Hey posts, DMs, files yes Per-capsule namespace under $DATA_DIR · capsule binaries refresh, user data does not
iroh node id yes Persisted in $DATA_DIR · DHT entries stay valid across restarts
Capsule bundles refreshed Capsule bundles ship inside the binary release · each upgrade re-stages them into $DATA_DIR/capsules/
Sessions, capability tokens no In-memory only · browser re-handshakes automatically via cookie → bearer endpoint
