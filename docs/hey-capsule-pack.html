Hey
Capsule Pack

Two browser apps + one native provider. Speaks only stable upstream contracts. Installs on any Elastos Runtime ≥ v0.3.0. Survives every future upstream release unchanged.

hey-social hey-messenger blobs-provider X25519 + ML-KEM-768 iroh-blobs

01What's in the pack

Three artifacts. The entire surface of Hey on top of an Elastos Runtime. Everything else — auth, storage, transport, content addressing — is upstream's job.

SPA

hey-social

Vite-built React SPA. Photo + video posts over Carrier gossip, IPFS-CID media, Ed25519-signed records. Per-account profile state lives at localhost://Users/self/.AppData/LocalHost/Hey/.

~800 KB bundle · ~80 source files

SPA

hey-messenger

Teams-shaped P2P messenger. Hybrid post-quantum E2E for DMs (X25519 + ML-KEM-768). Iroh-blobs file share. Workspace + channel + DM hierarchy on Carrier topics.

~250 KB bundle · client-side crypto · zero server logic

native

blobs-provider

Native Rust binary. Wraps iroh-blobs for unlimited-size P2P file transfer. Exposes /api/provider/blobs/{add_bytes,fetch,share,drop}. Upstream doesn't ship this — we wrote it.

~1 MB binary · holepunched QUIC · no size cap

Total Hey surface: two static SPA bundles + one native binary + their capsule.json manifests. That's everything Hey is. Mounting them onto an Elastos Runtime install is a directory copy.

02Contract with upstream

Hey calls only HTTP contracts upstream owns. The contracts are stable across releases — vN to vN+1 means a YunoHost-side version bump, not a Hey rewrite.

What Hey calls

  • /api/auth/passkey/* — passkey signup + signin (v0.3+ stable)
  • /api/provider/peer/* — Carrier gossip + DHT
  • /api/provider/blobs/* — our own provider, deterministic
  • /api/provider/ipfs/* — Kubo bridge
  • /api/provider/did/* — DID sign / verify / resolve
  • /api/localhost/* — sandboxed encrypted storage
  • /api/capability/request — manifest auto-grant

What Hey doesn't touch

  • Session registry internals
  • Capability token format
  • At-rest encryption envelope schema
  • Principal data model
  • Recovery Kit format
  • Wallet / browser / chain-provider APIs
  • Anything subject to vN→vN+1 churn

03Hybrid post-quantum E2E

Hey Chat DMs are encrypted with X25519 and ML-KEM-768 (NIST FIPS 203). Breaking the message requires breaking both primitives. Same hybrid pattern as Signal PQXDH.

Where the keys come from

From the user's passkey via the WebAuthn PRF extension. Same 32-byte PRF output deterministically derives the X25519 keypair AND the ML-KEM-768 keypair AND the Ed25519 signing keypair. One passkey tap → three keypairs. Lose the passkey, keep the recovery key, get the same three again.

Public-key discovery

Each peer publishes a self-signed bundle to a profile topic hey-msg/v0/profile/<did> with their X25519 + KEM pubkeys. Recipients fetch + verify the Ed25519 signature, then cache. First DM to someone takes ~250 ms; subsequent ones use the cache.

04Topic addressing

Carrier delivers pubsub on opaque topic ids. Hey decides how those ids encode messaging semantics — DM pairs, channels, profiles. The runtime never sees the structure.

PurposeTopic string
DM between two peers hey-msg/v0/dm/<sorted-didA>::<sorted-didB>
DIDs are sorted lexicographically so order doesn't matter — both peers compute the same string deterministically.
Channel message hey-msg/v0/ws/<workspaceId>/ch/<channelId>/msg
Profile bundle hey-msg/v0/profile/<did>
Self-signed X25519 + KEM pubkey advertisement. Subscribed-to by anyone who wants to DM that DID.
Global feed (Hey Social) hey-v0/posts/global
Public posts, signed by author's didKey.

Metadata vs content

Topic strings are visible to anyone joined to them. A Carrier-mesh observer can see that two specific DIDs are messaging each other and when. They cannot read content — that's hybrid-PQ encrypted inside the message payload. This is the same metadata trade-off Signal makes ("we know A is talking to B but not what they said"). Full metadata privacy would need onion routing layered on Carrier — not built.

05File share — iroh-blobs

Direct P2P transfer over holepunched QUIC. No upload step, no size cap, no third-party storage. The recipient stays offline until they tap the attachment — at which point Alice's box streams the bytes to Bob's box.

Alice attaches a file in the composer

Client reads the file as Uint8Array.

Stage locally via blobs-provider

POST /api/provider/blobs/add_bytes → blobs-provider hashes the bytes (BLAKE3), stores them under $data_dir/blobs/, returns { hash, ticket }.

Encode the ticket inside the encrypted message

Payload becomes { content: "📎 photo.jpg", attachments: [{ name, size, mime, ticket }] } — the ticket is wrapped by the PQ-hybrid encryption together with the message text, so no third party can synthesize a fetch.

Send over Carrier

gossip_send on the DM topic. Bob's inbox poller picks it up; ChaCha20-Poly1305 decrypt; ticket recovered.

Bob taps "download"

POST /api/provider/blobs/fetch { ticket, dest } → blobs-provider dials Alice's iroh node using the ticket's bootstrap hints, holepunched QUIC connects, bytes flow direct Alice→Bob, write to $data_dir/blobs/.

Render

UI streams the bytes from local disk — image preview / video player / opens with the OS handler.

Why we own this provider

Upstream ships ipfs-provider but no iroh-blobs provider. IPFS works for public content (photos, posts) but is wrong for E2E DM attachments — IPFS bytes are content- addressed-but-public, so anyone holding the CID can fetch. iroh-blobs is gated by the ticket (a self-contained dial string) which we embed inside the encrypted payload — only the recipient ever sees it.

06Distribution paths

The pack ships as a standalone unit. Three installation paths cover every operator scenario.

primary

YunoHost package

yunohost app install elastos-runtime_ynh bundles the upstream runtime + Hey capsule pack + frosted-glass theme + systemd glue + nginx config. One command, full setup.

standalone

Drop on bare runtime

Operators running upstream Elastos Runtime directly can install the pack with install-into-runtime.sh — verifies upstream deps (ipfs, did, peer), builds blobs-provider, copies SPA bundles, registers in components.json, restarts. No YunoHost required.

fork

Custom packaging

The pack lives in its own git repo with no YunoHost-specific code. Any operator can fork and re-package — different branding (via a different theme overlay), different deployment target, different SSO. Hey itself is unchanged.

Frosted-glass theme

The theme overlay is not part of the capsule pack — it lives in the YunoHost package's conf/ directory and gets appended to upstream's home capsule style.css at install time. This keeps the pack 100% portable: any Elastos Runtime install — themed or not, YunoHost or not — accepts the pack unchanged.
